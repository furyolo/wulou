# 分类模型接入方案调研

调研日期：2026-09-09

## 采用方案

采用“实时云端 API + 云端 Batch API”的混合方式，且两种方式都保持**每道题一条独立模型请求**。

- 当前页即时识别、人工修改后重判、失败重试：使用实时 API。
- 整个专题或多页题目的批量初分：导出 JSONL，提交云端 Batch API，完成后按题目 ID 导入。
- 不使用本地模型。
- 不把全部题目拼进一个超长提示词。

这里的“离线分类”只表示本地先导出任务、稍后导入结果；真正的推理仍在云端完成。更准确的名称是“云端异步批量分类”。

## 两种方式实际怎样调用

### 实时云端 API

逻辑上每题一次请求。本地服务可以同时处理少量题目，例如并发 3 至 5 条；每条请求都带有题目 ID、题干、必要时的答案或图片、当前专题候选目录、规则版本和 JSON Schema。

这种方式能在几秒到几分钟内逐步把结果显示到页面，适合用户正在浏览和审核的场景。

### 导出 JSONL 后批量分类

不是把全部题目一次性塞给模型。JSONL 每行是一道题的完整请求，一个批任务包含许多互相独立的请求：

```json
{"custom_id":"exercise-2529221","method":"POST","url":"/v1/responses","body":{"model":"<configured-model>","input":"<question-and-taxonomy>"}}
{"custom_id":"exercise-2529222","method":"POST","url":"/v1/responses","body":{"model":"<configured-model>","input":"<question-and-taxonomy>"}}
```

批任务完成后，服务用 `custom_id` 将乱序结果映射回 `exercise_id`，逐条校验并写入缓存。单题失败只重试该题。

OpenAI 官方说明 Batch 输入文件的每一行都是一个独立请求，参数与普通接口相同；Batch 费用比同步接口低 50%，有独立且更高的速率池，承诺在 24 小时内完成，单批最多 50,000 条请求或 200 MB。Google Gemini 和 Anthropic Claude 的官方 Batch 文档也采用独立请求集合，并都给出 50% 的批处理价格折扣和最长约 24 小时的完成窗口。

## 分类效果判断

实时和 Batch 使用相同的模型、输入、提示词、候选目录、结构化输出约束及推理参数时，预期分类能力相同。Batch 只是请求调度和计费方式不同。这个判断是根据各厂商文档中“批请求沿用普通请求参数、各条请求独立处理”作出的工程推断；模型输出仍可能有随机波动，不能只靠文档声称效果完全一致。

上线前要用同一批人工标注题做盲测：

1. 至少覆盖纯文本、公式、图形、跨专题、目录边界和无合适目录六类题目。
2. 实时与 Batch 使用完全相同的模型版本、提示词版本和输入。
3. 比较三级目录准确率、四级目录准确率、强制复核召回率、无效目录率和单题成本。
4. 若差异落在重复测试的随机波动范围内，则按成本和时效选择通道。

分类质量最关键的是输入与任务拆分：

- 一题一请求，避免题目之间互相干扰，并允许逐题重试和审计。
- 候选目录使用稳定 ID 和定义，不只给标题。
- 通过 JSON Schema 限制输出字段和枚举；程序仍要验证目录存在性、父子关系和规则版本。
- 文本优先；公式、图形、表格缺失或低置信度时才升级为图片输入。
- 已有目录分类与新目录发现分成两个阶段。

## 为什么不把全部题目放进一个请求

一个超长请求表面上像“一次分类全部题目”，实际有明显缺点：

- 任意一题导致格式错误或输出截断时，整批结果难以恢复。
- 不能只重试失败题，成本和故障影响范围更大。
- 多题上下文容易让分类依据互相污染。
- 输出数组与题目 ID 对齐更脆弱，审计困难。
- 题目数量受上下文和最大输出长度限制。

重复的目录与规则前缀可通过供应商的提示词缓存降低成本，不需要用超长多题请求来节省输入 token。

## 推荐的两阶段分类流程

### 第一阶段：逐题归入现有目录

1. 油猴脚本采集题目并交给 `127.0.0.1:3232`。
2. 本地服务完成标准化、候选目录收窄和缓存查询。
3. 当前页需要立即查看时走实时 API；专题批量任务写成 JSONL 后走 Batch API。
4. 每题返回唯一目录路径、置信度、依据、复核标记和规则版本。
5. 服务校验结果，不能唯一命中时进入人工复核或待聚类集合。

### 第二阶段：跨题聚类并提出新目录

只有现有目录无法覆盖的题目才进入这一阶段。服务先按数学对象、主问和决定性条件汇总题目特征，再让云端模型对同一专题内的待定题进行成组分析。

新目录候选必须满足项目既定规则：至少 3 道不同题目、优先复用旧目录、标题具有稳定检索价值，并经过语义审核和人工确认。通过审核后才分配 `SF` 编号并生成新的 Excel 版本。

这种全局分析才需要同时观察多道题，但输入应是经过脱敏和压缩的特征摘要及代表题，而不是把整批原始题目塞入第一阶段分类请求。

## 效率与成本比较

| 维度 | 实时 API | 云端 Batch API | 全部题目单请求 |
|---|---|---|---|
| 预期分类质量 | 同模型同输入时与 Batch 相当 | 同模型同输入时与实时相当 | 容易受长上下文、对齐和截断影响 |
| 首批结果速度 | 快，适合页面即时显示 | 慢，最长约 24 小时 | 单次等待，失败影响全部 |
| 大批量吞吐 | 受普通速率限制 | 独立批处理额度，适合整专题 | 受上下文和输出长度限制 |
| 价格 | 标准价格 | 主流供应商通常为标准价格的 50% | 可能少重复前缀，但失败重跑昂贵 |
| 失败重试 | 按题重试 | 按题重试或重建失败子集 | 通常整批重试 |
| 可审计性 | 高 | 高，按题目 ID 映射 | 较低 |
| 推荐用途 | 当前页、低置信度复核 | 多页、整个专题、夜间任务 | 不采用 |

在分类效果相当的前提下，批量任务的性价比更高；即时交互任务的实际效率更高。生产方案由本地服务按任务时效自动选择。

## 接入边界

本地服务保留统一的供应商适配层，业务层只使用 `classify_one`、`submit_batch`、`get_batch`、`import_batch_results` 四类能力。模型名称、API 密钥、实时并发数和批处理开关放在被 Git 忽略的本地配置中。

第一版只接入一家同时支持多模态、结构化输出和 Batch API 的云供应商。供应商和具体模型应通过人工标注集实测后固定；不要仅凭公开榜单决定。后续若需切换供应商，目录规则、缓存格式和油猴脚本不随之改变。
